# OpenAPI 3.1 and 3.2 Support

**Status:** Design approved
**Date:** 2026-05-11
**Scope:** Add typed bindings for OpenAPI 3.1.x and 3.2.x to the existing Kotlin Multiplatform library, alongside continued 3.0.x support.

## Goal

Today the library exposes a single `OpenAPIV3Model` `data class` that loosely represents 3.0 (with a few 3.1 affordances bolted on). We want to:

1. Parse and serialize OpenAPI 3.1.x and 3.2.x documents losslessly for the fields we model.
2. Surface version-specific additions as typed fields rather than as `xProperties` or raw `JsonElement` blobs.
3. Keep a single public entry point so callers don't have to choose between `OpenAPIV3` / `OpenAPIV31` / `OpenAPIV32`.
4. Fail loudly on unmodeled or version-inappropriate input — preserve the strict-by-default behavior the typed model is meant to give callers.

Non-goals: YAML input, JSON Schema 2020-12 identifier/anchor plumbing (`$id`, `$anchor`, `$dynamicRef`, `$dynamicAnchor`, `$schema`, `$comment`), every 3.2 minor keyword. These either remain as future work or, if encountered in input, throw under strict mode.

## API shape

`OpenAPIV3Model` becomes a sealed interface with three data-class implementers:

```kotlin
sealed interface OpenAPIV3Model {
    val openapi: String
    val info: InfoObject
    val externalDocs: ExternalDocumentation?
    val tags: List<TagObject>?
    val security: List<Map<String, List<String>>>?
    val servers: List<Server>?
    val xProperties: Map<String, JsonElement>?
    // `paths` drops to optional because 3.1 made it non-required
    val paths: Map<Path, PathItem>?
}

data class OpenAPIV30Model(...) : OpenAPIV3Model   // current fields
data class OpenAPIV31Model(...) : OpenAPIV3Model   // + webhooks, jsonSchemaDialect, ...
data class OpenAPIV32Model(...) : OpenAPIV3Model   // + 3.2 additions
```

`OpenAPIV3.decodeFromString` reads the `openapi` field, parses MAJOR.MINOR, dispatches to the matching subclass. `OpenAPIV3.encodeToString` calls the sealed interface's polymorphic serializer, which routes to the subclass's own `data class` serializer.

The same pattern repeats for `OpenAPIV3Schema` (sealed → `OpenAPIV30Schema` / `OpenAPIV31Schema` / `OpenAPIV32Schema`) and for each `XOrReference` family. Per-version `Reference` types stay separate because their permitted sibling fields differ.

## Module layout

```
commonMain/.../bindings/
  OpenAPIModel.kt              # shared interfaces (small additions)
  OpenAPIV3.kt                 # entry point — gains version dispatch
  OpenAPIV3Model.kt            # sealed interface only
  v30/OpenAPIV30Model.kt       # 3.0 data classes (renamed from current)
  v30/OpenAPIV30Serializers.kt
  v31/OpenAPIV31Model.kt
  v31/OpenAPIV31Serializers.kt
  v32/OpenAPIV32Model.kt
  v32/OpenAPIV32Serializers.kt
  OpenAPISpecification.kt      # xProperties traversal — regex extended
  Version.kt                   # gains V30/V31/V32, drops V3
```

Each minor's file pair stays at a comparable size to the current `OpenAPIV3Model.kt` / `OpenAPIV3Serializers.kt`. Diffs reviewable per version.

## Per-version field additions

This is the scope contract. Anything outside this list is out of scope and, if encountered in input, throws under strict mode.

### `OpenAPIV31Model` (vs `OpenAPIV30Model`)

Document level:
- `webhooks: Map<String, OpenAPIV31PathItemOrReference>?`
- `jsonSchemaDialect: String?`
- `paths: Map<Path, OpenAPIV31PathItem>?` (was required → now nullable)

Components (`OpenAPIV31Components`):
- Adds `pathItems: Map<String, OpenAPIV31PathItemOrReference>?`.

Info / License (shared types, both fields nullable so safe to add to the shared class):
- `InfoObject.summary: String?`
- `LicenseObject.identifier: String?` (SPDX; spec says mutually exclusive with `url`, we don't enforce that).

Schema (`OpenAPIV31Schema` vs `OpenAPIV30Schema`):
- **Drops** `nullable` (removed in 3.1; use `["...", "null"]` instead).
- **Changes** `exclusiveMinimum: Boolean?` → `Double?`; same for `exclusiveMaximum`.
- **Adds** JSON Schema 2020-12 keywords:
  - `const: JsonElement?`
  - `prefixItems: List<OpenAPIV31SchemaOrReference>?`
  - `contentEncoding: String?`, `contentMediaType: String?`, `contentSchema: OpenAPIV31SchemaOrReference?`
  - `dependentRequired: Map<String, List<String>>?`
  - `dependentSchemas: Map<String, OpenAPIV31SchemaOrReference>?`
  - `unevaluatedProperties: OpenAPIV31SchemaOrReferenceOrBoolean?`
  - `unevaluatedItems: OpenAPIV31SchemaOrReference?`
  - `$defs: Map<String, OpenAPIV31SchemaOrReference>?`
- **Carries over** from the existing model: `type` as single-or-array via `OpenAPIV3TypeDefinition`, `"null"` type enum, `propertyNames`, `examples` array, `$ref` siblings.

Reference (`OpenAPIV31Reference`): allows `summary` and `description` siblings (already present in current `OpenAPIV3Reference`); no further change.

### `OpenAPIV32Model` (vs `OpenAPIV31Model`)

PathItem and Operation:
- `OpenAPIV32PathItem.query: OpenAPIV32Operation?` — new HTTP method in 3.2.
- `OpenAPIV32PathItem.additionalOperations: Map<String, OpenAPIV32Operation>?` — non-standard verbs.

Tags (shared type, both fields nullable so safe to add to shared `TagObject`):
- `TagObject.parent: String?`
- `TagObject.kind: String?`
- `TagObject.summary: String?`

Schema (`OpenAPIV32Schema`):
- Same field set as `OpenAPIV31Schema` for this scope. The distinct subclass exists so future 3.2-only keywords have a home and so per-version `XOrReference` discriminators line up.

### Shared / common-interface changes

- `OpenAPIModel.paths` drops to nullable (matches 3.1 spec; non-breaking for callers reading the field).
- `Version` enum gains `V30, V31, V32`; `V3` is removed.
- New `Version.fromOpenApiString(value: String): Version` helper: parses `MAJOR.MINOR.PATCH`, throws `IllegalStateException("Unsupported OpenAPI version: <value>")` for anything outside `2.0`, `3.0.x`, `3.1.x`, `3.2.x`.

## Serializers and version dispatch

### Top-level dispatch (`OpenAPIV3.decodeFromString`)

```kotlin
fun decodeFromString(string: String): OpenAPIV3Model {
    val tree = json.decodeFromString<JsonObject>(string)
    val openapi = tree["openapi"]?.jsonPrimitive?.contentOrNull
        ?: error("No valid openapi v3 element 'openapi' is missing")
    val version = Version.fromOpenApiString(openapi)
    val decoded = tree.decode(version)               // existing xProperties pass
    return when (version) {
        V30 -> json.decodeFromJsonElement<OpenAPIV30Model>(decoded)
        V31 -> json.decodeFromJsonElement<OpenAPIV31Model>(decoded)
        V32 -> json.decodeFromJsonElement<OpenAPIV32Model>(decoded)
        V2  -> error("V2 documents are not supported by OpenAPIV3")
    }
}
```

Encode is symmetric — the sealed interface has a polymorphic serializer that routes to the subclass's own `data class` serializer.

### Per-version `XOrReference` families

Each minor gets its own sealed `OpenAPIV3xSchemaOrReference`, `OpenAPIV3xResponseOrReference`, etc. with its own discriminator serializer following the current pattern (`tree.containsKey("$ref")` branches to `Reference` else to the concrete type). They cannot be unified because the underlying `Schema` and `Reference` differ per minor.

To keep this duplication readable, introduce a small internal helper:

```kotlin
internal inline fun <reified T, reified R, reified S> JsonDecoder.decodeOrRef(
    tree: JsonObject,
    referenceSerializer: KSerializer<R>,
    schemaSerializer: KSerializer<S>,
): T where T : Any, R : T, S : T = when {
    tree.containsKey("\$ref") -> json.decodeFromJsonElement(referenceSerializer, tree) as T
    else                     -> json.decodeFromJsonElement(schemaSerializer, tree) as T
}
```

(Final signature may differ; intent is to reduce the ~12 near-identical serializers per version to a one-liner each.)

### xProperties traversal (`OpenAPISpecification.kt`)

The existing regex list is extended with paths introduced by 3.1/3.2:

- `^|webhooks|[^|]*|x-[^|]*|$`
- `^|webhooks|[^|]*|[^|]*|x-[^|]*|$`
- `^|components|pathItems|[^|]*|x-[^|]*|$`
- `^|prefixItems|[^|]*|x-[^|]*|$`
- `^|dependentSchemas|[^|]*|x-[^|]*|$`
- `^|$defs|[^|]*|x-[^|]*|$`
- `^|additionalOperations|[^|]*|x-[^|]*|$`

`OpenAPISpecification.validate` keeps the `openapi` key requirement; the value is parsed by `Version.fromOpenApiString` to determine the variant.

### Strict mode

`Json { prettyPrint = true }` keeps `ignoreUnknownKeys = false` (the kotlinx-serialization default). Unmodeled keywords throw across all three versions:

- Unmodeled 2020-12 keywords (`$id`, `$anchor`, `$dynamicRef`, `$dynamicAnchor`, `$schema`, `$comment`) → throw.
- 3.1-only fields in a `3.0.x` doc (e.g. `webhooks`) → version dispatch picks `OpenAPIV30Model`, then strict-mode rejection fires with the field name.
- Malformed `openapi` string → `Version.fromOpenApiString` throws with a clear message.

This preserves lossless roundtrip for everything we model and surfaces everything else loudly. If a user hits a real-world doc using an unmodeled keyword, the path forward is to model the keyword (i.e. expand scope), not to silently drop it.

**Caveat on shared-type additions.** Strict-mode rejection works field-by-field at the kotlinx-serialization layer, so it catches wrong-version usage only when the field is *absent* from the per-version data class. For fields added to the *shared* types — `InfoObject.summary`, `LicenseObject.identifier`, `TagObject.{parent,kind,summary}` — a 3.0 document can use them without erroring, because the shared class accepts them. We accept this trade-off: forking `InfoObject` / `LicenseObject` / `TagObject` per minor would triple the type surface for fields that are pure additive metadata. Strict cross-version checks for these specific fields can be added later as an explicit validation pass if a caller needs it.

## Testing

The existing roundtrip contract — `it shouldEqualJson it.let(decode).let(encode)` — is the primary check; we extend it rather than invent a new pattern.

### Fixtures

```
src/commonTest/resources/examples/
  v3/   (existing — stays for 3.0.x docs)
  v31/  (new)
  v32/  (new)
```

- Move `mastodon.json` to `v31/` (it is a 3.1.0 doc per the PR #9 commit message). Keep the rest of the current corpus in `v3/`.
- Add a small hand-rolled `v31/feature-coverage.json` exercising: `webhooks`, `jsonSchemaDialect`, `paths` omitted, `components.pathItems`, Info `summary`, License `identifier`, schema with `const`, `prefixItems`, `contentEncoding` / `contentMediaType`, `dependentRequired`, `dependentSchemas`, `unevaluatedProperties`, `unevaluatedItems`, `$defs`, numeric `exclusiveMinimum`/`exclusiveMaximum`.
- Add `v32/feature-coverage.json` exercising: `query` HTTP method on a `PathItem`, `additionalOperations`, extended `tags` (`parent`, `kind`, `summary`), at minimum.

### Test classes

- Split tests into `OpenAPIV30Tests.kt` (renamed from the current `OpenAPIV3Tests.kt` body for 3.0 docs), `OpenAPIV31Tests.kt`, `OpenAPIV32Tests.kt`. Each runs roundtrip over its fixtures.
- Add targeted decode assertions in each (separate from roundtrip) to prove version dispatch picks the right subclass:
  - `OpenAPIV3.decodeFromString(v31Doc) is OpenAPIV31Model`
  - `OpenAPIV3.decodeFromString(v32Doc) is OpenAPIV32Model`
- Strict-mode negative tests:
  - `openapi: "3.0.0"` with a `webhooks` field → throws.
  - `openapi: "3.1.0"` with `$dynamicAnchor` somewhere → throws.
  - `openapi: "3.3.0"` → throws `Unsupported OpenAPI version: 3.3.0`.
- Preserve the existing "V2 passed to V3" negative test, updating its expected message if we change it.

No new Gradle wiring; common/jvm sources and the `kotest` matchers already cover this.

## Build sequence (for the implementation plan)

A reasonable ordering — the implementation plan from `writing-plans` will refine this:

1. **Version enum + parser.** Replace `V3` with `V30/V31/V32`, add `fromOpenApiString`, update `OpenAPISpecification.validate` to call it. No behavior change yet (decoder still routes everywhere to the single existing model).
2. **Rename current model to V30.** Rename `OpenAPIV3Model` data class → `OpenAPIV30Model`. Introduce `sealed interface OpenAPIV3Model` with `OpenAPIV30Model` as its only implementer. Move 3.0 files under `v30/`. Tests still pass; only types renamed.
3. **Wire top-level dispatch in `OpenAPIV3.decodeFromString`.** Reads `openapi`, dispatches via `Version.fromOpenApiString`. Still only V30 exists; the V31/V32 branches throw a TODO for now.
4. **Build `OpenAPIV31Model` family.** Mirror V30 file structure under `v31/`. Add the per-version field set above. Wire its serializers. Hook into top-level dispatch.
5. **Move mastodon fixture to `v31/`, add `v31/feature-coverage.json`, add `OpenAPIV31Tests.kt`.** Roundtrip and dispatch assertions.
6. **Build `OpenAPIV32Model` family.** Mirror V31. Add Tag-shared extensions; add `query` / `additionalOperations` on PathItem.
7. **Add `v32/feature-coverage.json`, `OpenAPIV32Tests.kt`.**
8. **Extend xProperties regex list** in `OpenAPISpecification.kt` for new paths.
9. **Strict-mode negative tests** for each rejection case in the spec above.
10. **README and changelog updates** documenting the breaking changes from §"Breaking changes" below.

## Breaking changes (for README / changelog)

1. `OpenAPIV3Model` is now a sealed interface. Field reads against it still compile; instantiation and `copy()` move to `OpenAPIV30Model`.
2. `Version.V3` is replaced by `Version.V30`, `V31`, `V32`.
3. `OpenAPIV3.decodeFromString` now dispatches by version string. A `3.1.0` document that previously decoded into the same data class as 3.0 (silently dropping 3.1-only fields) now decodes into `OpenAPIV31Model` and surfaces those fields typed.
4. Schema `exclusiveMinimum` / `exclusiveMaximum` change from `Boolean?` → `Double?` on `OpenAPIV31Schema` and `OpenAPIV32Schema`. `OpenAPIV30Schema` keeps `Boolean?`.
5. Strict mode is unchanged for 3.0 docs; for 3.1/3.2 it newly rejects unmodeled JSON Schema 2020-12 keywords. Users hitting one in the wild should request scope expansion.

The library is at 0.1.x; pre-1.0 semantics allow these changes without a major bump, but the changelog should call them out explicitly.
